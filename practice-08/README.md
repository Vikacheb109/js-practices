## 5. Загрузка через useEffect

Для загрузки используется эффект, зависящий от:

- api;
- q;
- completed;
- priority;
- categoryId;
- revision.

При запуске устанавливается `status = "loading"` и очищается ошибка загрузки.

Вызов `api.loadInitialData()` получает задачи и категории.

При успешном результате сохраняется новый snapshot и устанавливается `status = "ready"`.

При ошибке загрузки устанавливается `status = "error"`, а последний успешный snapshot не удаляется.

Пустой успешный список также относится к состоянию ready.

## 6. Отмена и устаревшие ответы

Каждый запуск эффекта создаёт собственный AbortController.

При изменении фильтра или размонтировании cleanup отменяет запрос и делает его неактуальным.

Перед обновлением данных и перед отображением ошибки проверяется, что запрос по-прежнему актуален.

В режиме разработки StrictMode может создавать дополнительную пробную загрузку, которую cleanup отменяет.

## 7. Операции изменения данных

Создание: POST.

Редактирование и переключение статуса: PATCH.

Удаление: DELETE.

Сброс: POST `/api/debug/reset`.

Операции выполняются через общую функцию mutate.

Для предотвращения двойного сохранения используется useRef. Блокировка устанавливается до первого await.

При успехе операция возвращает true и увеличивает revision, что запускает новый GET.

При ошибке операция возвращает false, сохраняет mutationError и не изменяет последний успешный snapshot.

## 8. Разделение ошибок изменения и загрузки

Ошибка POST, PATCH или DELETE хранится в mutationError.

Ошибка GET хранится отдельно в error.

Если POST подтвердил успех, но повторный GET завершился ошибкой, изменение считается успешным. Пользователю показывается ошибка обновления списка.

Автоматически повторять POST нельзя, поскольку повтор может создать дублирующуюся задачу.

При неуспешном сохранении значения формы сохраняются.

## 13. Ответы на контрольные вопросы

**1. Зачем нужен useEffect?** Для синхронизации интерфейса с внешним сервером после рендера. Запрос в теле компонента вызывался бы при каждом рендере.

**2. Когда вызывается cleanup?** Перед новым запуском эффекта с изменёнными зависимостями и при размонтировании компонента.

**3. Почему useEffect не async?** Эффект должен возвращать функцию очистки или ничего, а async-функция возвращает Promise.

**4. Какие зависимости нужны?** Стабильный api, значения четырёх фильтров и revision. Snapshot является результатом загрузки, поэтому в зависимости не включается.

**5. Почему api должен быть стабильным?** Новая ссылка на api при каждом рендере могла бы запускать бесконечные загрузки.

**6. Зачем проверять актуальность ответа?** AbortController не гарантирует, что все реализации запросов прекратят выполнение. Старый ответ необходимо дополнительно игнорировать.

**7. Почему проверка нужна в catch?** Запоздавшая ошибка старого запроса не должна заменить состояние актуального результата.

**8. Что делает StrictMode?** В режиме разработки помогает обнаружить неправильные побочные действия и очистку эффектов.

**9. Почему недостаточно pending?** Два синхронных вызова могут увидеть старое значение состояния. Ref блокирует повтор сразу.

**10. Что означает true от saveTask?** Сервер подтвердил запись. Следующий GET может завершиться ошибкой, но это не отменяет успех записи.

**11. Почему нельзя автоматически повторять POST?** Сервер мог выполнить первый POST, даже если его ответ потерялся. Повтор способен создать дубликат.

**12. Почему фильтр не отменяет изменение?** Чтение и мутация используют разные AbortController. Изменение фильтра отменяет только чтение.

**13. Что означает отмена клиентского запроса?** Она прекращает ожидание на клиенте, но не гарантирует отмену уже выполненного сервером изменения.

**14. Что такое meta.total?** Число записей в последней серверной выборке с применёнными фильтрами, а не всегда общее число задач на сервере.

**15. Что требует настоящего браузера?** Проверка CORS, Network, фактической работы формы, внешнего вида и пользовательских действий.
