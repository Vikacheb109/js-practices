## 4. Архитектура приложения

| Модуль | Назначение |
|---|---|
| `api-client.js` | Общий HTTP-клиент, запросы, JSON, ошибки и отмена |

Сервер является единственным источником актуальных задач. После успешной операции изменения интерфейс повторно получает список по HTTP.

## 5. Работа с HTTP

Реализованы методы:

| Метод | Назначение |
|---|---|
| GET | Получение задач и категорий |
| POST | Добавление задачи и сброс учебных данных |
| PATCH | Изменение задачи или статуса |
| DELETE | Удаление задачи |

При наличии тела запроса оно преобразуется в JSON. Для JSON добавляется заголовок `Content-Type: application/json`.

При статусе `204 No Content` функция возвращает `null`, не пытаясь разобрать пустое тело.

Ошибки классифицируются по видам `http`, `network`, `invalid-response`, `timeout` и `aborted`.

## 6. Состояния интерфейса

| Состояние | Значение |
|---|---|
| `loading` | Задачи загружаются |
| `ready` | Список успешно получен |
| `empty` | Запрос успешен, но задач по фильтру нет |
| `error` | Загрузка не удалась |

Ошибочная загрузка не изменяет подтверждённые сервером данные. Пользователю выводится сообщение и предоставляется возможность повтора.

## 7. Защита от устаревших ответов

При новой загрузке предыдущий запрос отменяется через `AbortController`.

Каждому запросу назначается номер. После получения ответа контроллер проверяет, совпадает ли номер с последней загрузкой.

Если ответ относится к устаревшему запросу, он не применяется к интерфейсу.

Отмена запроса при смене фильтра не считается пользовательской ошибкой.

## 8. Создание, редактирование и удаление задач

Форма поддерживает добавление и редактирование.

Введённые данные проверяются через `validateTaskDraft`, после чего отправляются на сервер.

Создание выполняется через POST, редактирование — через PATCH.

Для изменения статуса отправляется поле `completed`.

Для удаления используется DELETE.

После успешной операции выполняется повторная загрузка актуального списка с текущими фильтрами.

На время изменения кнопки блокируются, чтобы исключить повторное отправление операции при двойном нажатии.

## 12. Ответы на контрольные вопросы

**1. Почему fetch не считает 404 сетевой ошибкой?** Потому что HTTP-ответ успешно получен. Для обнаружения HTTP-ошибки проверяется `response.ok`.

**2. Как проверяется ответ?** Сначала успешность статуса, затем случай 204, затем Content-Type и JSON.

**3. Чем POST отличается от PATCH?** POST создаёт задачу, PATCH изменяет поля существующей задачи.

**4. Для чего нужны 201 и Location?** Статус 201 подтверждает создание, а заголовок Location указывает адрес нового ресурса.

**5. Почему нельзя вызывать json() при 204?** У такого ответа отсутствует тело.

**6. Что такое CORS?** Механизм браузера, контролирующий доступ к ресурсам другого origin. Режим no-cors не позволяет обычным образом читать закрытый ответ.

**7. Чем empty отличается от error?** Empty означает успешный запрос без записей, error — неуспешную загрузку.

**8. Почему больше не используется localStorage для задач?** Потому что источником актуального состояния является сервер.

**9. Почему после изменения нужен новый GET?** Чтобы интерфейс показывал подтверждённое сервером состояние.

**10. Что такое гонка запросов?** Ситуация, когда старый запрос завершается позже нового и может перезаписать актуальный результат.

**11. Зачем номер запроса вместе с AbortController?** Даже после попытки отмены старый запрос может завершиться, поэтому дополнительно проверяется актуальность его номера.

**12. Почему отмена не показывается как ошибка?** Она может быть нормальным результатом смены фильтра пользователем.

**13. Кто проверяет данные?** Клиент проверяет их перед отправкой, а сервер повторяет проверку независимо.

**14. Зачем передавать view в контроллер?** Чтобы логика управления не зависела от DOM и могла проверяться отдельно.

**15. Почему textContent?** Чтобы серверные строки отображались как текст, а не интерпретировались как HTML.
